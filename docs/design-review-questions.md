### Q1. Agent 的"可见消息历史"范围

**问题描述**：
PRD 5.4.4 定义"每个 Agent 独立维护其可见消息历史，包含该 Agent 参与的所有会话"。Prompt 拼接第 4 层会注入所有私聊+群聊的历史。但用户界面中每个会话只展示当前会话的消息。

**矛盾点**：Agent 在 Prompt 中能看到跨会话的历史（如私聊A中知道群聊B的对话），但用户在看私聊A界面时看不到群聊B的消息。这是否会导致 Agent 的回复让用户感到"跳跃"？

**备选项**：
- **A. 全局可见**（当前 PRD 设计）：Agent 的 Prompt 包含其参与的所有会话历史。Agent 可能基于群聊内容回复私聊。
- **B. 会话隔离**：Agent 的 Prompt 只包含当前会话的历史。跨会话信息不互通，Agent 在每个会话中独立。
- **C. 混合模式**：当前会话历史全量注入，其它会话历史以摘要/近期 N 条形式注入。

**推荐：B 或 C**。A 的问题是 Agent 可能在私聊中引用群聊内容，用户会感到困惑。B 最符合 IM 直觉（微信里 Alice 不会把你和 Bob 的私聊内容拿出来说）。C 是折中，但实现复杂。


回答：A。全局可见，以人作为用户的视角来看，人能同时看到私聊消息和群聊消息，也预期会在对应的窗口回复对应的消息，需要在系统提示词中强调，让AI能够选择正确的回答窗口。

### Q2. Agent-Agent 私聊的创建方式

**问题描述**：
PRD 5.4.8 提到"Agent A → Agent B（两个 Agent 的私聊）"，但 PRD 5.3.1 和 feature_list.md SES-01 只说"用户选择一个 Agent 创建私聊"。Agent-Agent 私聊由谁创建？如何创建？

**备选项**：
- **A. 用户代理创建**：用户在创建会话时可以选择"1对1（Agent vs Agent）"模式，替两个 Agent 创建会话。
- **B. Agent 自主创建**：Agent 可以通过 send_message Tool 的扩展参数（如 `create_private_chat`）主动发起私聊。这需要在 Tool Schema 中增加新工具。
- **C. 暂时不支持**：MVP 只支持"用户 vs Agent"私聊，Agent-Agent 对话仅在群聊中发生。P2 再考虑。

**推荐：C（MVP 阶段）**。Agent 自主创建会话会大幅增加复杂度（会话生命周期管理、循环创建风险）。且 PRD 迭代规划中 Phase 2 才实现 1对1 聊天，可先做用户-Agent 私聊。

回答：B，添加新工具支持agent自主发起私聊对话，发起私聊对话之后视为好友。

### Q3. `auto_mode_delay` 字段的实际语义

**问题描述**：
schema.md 中 `group_sessions.auto_mode_delay` 默认 5 秒，注释为"自动模式轮询延迟"。但 PRD 5.4.9 描述群聊触发是**事件驱动**（每条消息触发所有其它 Agent），不是 SillyTavern 的定时轮询。

**矛盾点**：如果是事件驱动，就不需要轮询延迟。这个字段的含义是什么？

**备选项**：
- **A. 事件驱动缓冲延迟**：群聊中消息到达后，不立即触发，而是等待 N 秒，如果期间没有新消息再统一触发。避免用户连续发多条消息时 Agent 每条都响应。
- **B. 删除该字段**：纯事件驱动不需要此字段。schema.md 中移除 `auto_mode_delay`。
- **C. 保留为轮询模式选项**：支持两种模式切换（事件驱动 vs 定时轮询），`auto_mode_delay` 在轮询模式下生效。

**推荐：A**。纯事件驱动下用户连发 3 条消息，Agent 会被触发 3 次（虽然间隔会过滤掉部分）。加入缓冲延迟（如 2 秒）可以让 Agent 等用户说完再回复，更像人类。但字段名应改为 `event_buffer_delay` 或 `trigger_cooldown`。

回答：A，以事件驱动为主。另外，应该有限制每个agent被触发的频率（默认30s），这个是用于避免连续多条消息导致重复触发的。如果这个auto_mode_delay字段不用于该功能，则删除auto_mode_delay字段

### Q4. 会话删除后的数据保留策略

**问题描述**：
feature_list.md SES-04 说"删除后可选是否保留聊天记录"。但 schema.md 中 `sessions`、`private_sessions`、`group_members`、`messages` 都设置了 `ON DELETE CASCADE`。如果删除会话时选择"保留聊天记录"，消息将失去 `session_id` 关联变成孤儿数据。

**备选项**：
- **A. 物理删除会话 + 级联删除所有消息**（当前 schema 设计）：删除即彻底清空，不可恢复。UI 上不提供"保留"选项。
- **B. 会话软删除**：给 `sessions` 表增加 `is_deleted` 字段。删除时标记为已删除，消息保留。UI 上可选择"彻底删除"或"仅移除会话列表"。
- **C. 归档模式**：删除会话时，将该会话的消息导出到归档表 `archived_messages`，然后从活跃表中删除。

**推荐：B**。与 feature_list.md 的"可选保留聊天记录"一致，且实现简单。只需在 sessions 表加 `is_deleted` 和 `deleted_at` 字段。
回答：基于B，提供一个清空聊天记录的选项，将清空的数据归档，在前端上的表现就是显示在一个单独的列表当中，但是私聊和群聊关系不删除，后续agent再次聊天就是一个新的session。

### Q5. 消息上限的计数基准（边界情况）

**问题描述**：
PRD 5.4.7 和 schema.md 7.4 用"自上次用户消息以来"的 Agent 消息数作为计数。SQL 中使用 `IFNULL(l.ts, 0)`，意味着如果会话开始以来**从未有过用户消息**，计数从会话创建时间（created_at ≈ 0）算起。

**场景**：用户创建一个群聊，开启禁言，然后让 Agent 们自己聊了 30 条。此时关闭禁言，用户发一条消息——按当前逻辑，计数重置为 0，Agent 还能再聊 30 条。这是预期行为吗？

**备选项**：
- **A. 保持当前逻辑**（`IFNULL(l.ts, 0)`）：从会话开始算起，用户消息重置计数。
- **B. 以会话创建时间为基准**：不使用 `IFNULL(l.ts, 0)`，而是 `IFNULL(l.ts, session_created_at)`。这样即使从未有用户消息，计数也从会话创建开始。
- **C. 显式计数器字段**：在 `private_sessions` / `group_sessions` 中增加 `agent_message_count` 和 `last_reset_at` 字段，用应用层维护计数，不依赖 SQL 查询。

**推荐：B**。A 的问题是如果会话创建于 t=1000，之前的历史消息也会被计入（虽然实际上不会有）。B 更精确。C 引入了计数器一致性问题，不推荐。
回答：没懂给出的意思，总之预期行为是：创建了群聊或者清空会话后或者用户说话后，重置计数，用一个字段维护计数即刻。另外，在计数结束后，能够在前端提供选项重置计数，而不是一定需要用户发送消息才能重置。

### Q6. 系统提示词（Prompt 第1层）是否可编辑

**问题描述**：
PRD 5.4.5 第1层是"系统提示词"，示例为"你是一个正在参与即时通讯聊天的 AI 角色..."，但没有说明这是固定的还是用户可配置的。

**影响**：如果可编辑，需要存储位置（全局设置表？per-Agent？）。如果固定，需要确认内容是否足够覆盖所有场景。

**备选项**：
- **A. 全局固定不可编辑**：系统提示词是硬编码的，所有 Agent 共享。确保行为一致性。
- **B. 全局可编辑**：在 app_settings 中增加 `global_system_prompt` 字段，用户可修改。影响所有 Agent。
- **C. Per-Agent 可编辑**：每个 Agent 可覆盖全局系统提示词。增加 `agents.system_prompt_override` 字段，NULL 表示使用全局默认值。

**推荐：B**。固定的系统提示词可能不适用于所有场景（如用户想强调"不要过度热情"）。全局可编辑足够，per-Agent 过于复杂。
回答：先做成固定的，在代码中写死。

### Q7. 群聊多 Agent 并发回复的展示策略

**问题描述**：
PRD 5.4.9 说"按生成完成的时间顺序依次展示"。但没有明确：Agent A 生成完成后是**立即展示**其消息，还是**等待所有被触发的 Agent 都完成后再批量展示**？

**场景**：群聊中 5 个 Agent 被触发，A 1秒后完成，B 10秒后完成。如果 A 立即展示，用户会在 B 还在生成时看到 A 的消息。这可能导致 A 的消息又触发一轮新的响应（如果禁言关闭）。

**备选项**：
- **A. 来一个展示一个**（流式展示）：Agent 生成完成后立即写入消息表并展示。最实时，但可能导致级联触发。
- **B. 批量展示**：等待本轮所有被触发的 Agent 都完成（或超时）后，一次性按时间排序展示。避免级联触发，但延迟较大。
- **C. 单队列顺序生成**：不按 PRD 说的"并行拉起"，而是像 SillyTavern 一样逐个串行生成。避免并发和级联，但速度较慢。

**推荐：A + 缓冲期**。来一个展示一个，但加入一个小缓冲期（如 2 秒）。在这 2 秒内到达的 Agent 回复批量展示，超过 2 秒的单独展示。这平衡了实时性和级联风险。或者更简单地：严格按事件驱动，但 Agent 回复写入消息后，**只有非发送者才被触发**，且受间隔约束，级联可控。
回答：立即显示，同上，有限制每个agent被触发的频率（默认30s）的机制，来避免连续触发。用户就应该及时看到已经生成完毕的消息（模拟人群聊，有人发送了就立刻显示）。注意，前端的流式输出显示是不需要的。在私聊中，如果是用户和agent的私聊窗口，在流式输出时显示“正在输入中”（低优先级），在群聊中不做任何显示。

### Q8. Token 预算与历史消息截断策略

**问题描述**：
reference.md 强调 Token 预算管理是 SillyTavern 的核心能力，但 PRD 中完全没有定义 AgentStage 的截断策略。当 Agent 参与多个会话、历史消息很长时，Prompt 可能超出模型上下文限制。

**备选项**：
- **A. 固定条数截断**：每个会话保留最近 N 条消息（如私聊最近 20 条，群聊最近 30 条）。简单但粗暴。
- **B. Token 预算动态截断**：计算 Prompt 各层 token 数，优先截断历史消息（第4层），保留系统提示词、人设、参与者简介。使用 `@dqbd/tiktoken` 本地计算。
- **C. 时间窗口截断**：只保留最近 1 小时/24 小时的消息。不符合角色扮演场景（用户可能隔几天继续聊）。

**推荐：B**。这是行业标准做法。PRD 应在非功能需求或详细功能中补充 Token 预算管理要求。MVP 阶段可先实现 A，P1 实现 B。
回答：最终使用B方案，但是放到中优先级，在初版实现中可以不进行截断，因为聊天记录单条内容短，可以支撑很多条。

### Q9. 用户与 Agent 的"好友关系"缺失

**问题描述**：
schema.md `friendships` 表只记录 Agent-Agent 关系（`agent_id_1`, `agent_id_2`）。但 PRD 5.4.5 参与者简介中包含用户（或用户人设）。用户和 Agent 之间是否需要某种关系记录？

**场景**：用户和 Agent Alice 有私聊，Alice 的参与者简介中应如何标注用户？"好友"？"聊天对象"？

**备选项**：
- **A. 不需要独立关系表**：用户和 Agent 只要有私聊，就自动视为"好友"。在 Prompt 中固定标注为"你的好友"或"正在与你聊天的用户"。
- **B. 扩展 friendships 表**：增加 `participant_type` 字段，支持 `agent-agent` 和 `user-agent` 关系。但用户是单一实体，不需要复杂关系。
- **C. 在私聊会话中隐式处理**：私聊场景的参与者简介直接固定生成，不查 friendships 表。

**推荐：C**。最简单。私聊中对方就是聊天对象，不需要查关系表。群聊中的用户也是"群友"，与 Agent 的关系通过 `friendships` 中的 Agent-Agent 关系区分"好友"和"群友"标签。
回答：所有agent都是用户的好友，在聊天标注时，直接标注为用户。进阶方案中有给用户包装人设的功能，该功能启用后，就会代替掉用户的简单标注。

### Q10. `personality` / `scenario` / `example_messages` / `first_message` 在 Prompt 中的位置

**问题描述**：
schema.md `agents` 表有 `personality`、`scenario`、`example_messages`、`first_message` 字段，但 PRD 5.4.5 的 Prompt 拼接（5层结构）中没有说明这些字段如何使用。

  2d. 示例对话：{example_messages}

回答：以A为主，这些字段用于构建更完整的agent性格，但在实际提示词中不用全部注入，只给出detailed_persona，后续会增加让agent自我迭代升级人设的功能，其它字段需要用在该功能上，让agent更新自己的detailed_persona

### Q11. 流式响应的展示方式

**问题描述**：
tech-stack.md 提到 SSE 流式响应，Rust 后端通过 Tauri Event 推送到前端。但 PRD 没有明确前端是逐字展示（打字机效果）还是等全部生成完再展示。

**备选项**：
- **A. 逐字流式展示**：前端实时显示 Agent 正在输入的内容，类似 ChatGPT。体验最佳，但实现复杂（需要处理 Markdown 渲染的中断状态）。
- **B. 等完成后一次性展示**：Agent 生成期间显示"正在输入..."，完成后整段消息展示。实现简单，但用户等待时看不到内容。
- **C. 按句子/段落流式**：不是逐字，而是每生成一个完整句子就展示一句。折中方案。

**推荐：A**。这是现代 AI 聊天应用的标准体验。虽然实现复杂，但 tech-stack 已选型 SSE + Tauri Event，具备实现条件。

回答：B，私聊时在ui上显示正在输入，群聊时先不做显示，模拟真实IM使用场景，IM中人和人聊天不会一个字一个字蹦出来。

### Q12. 消息上限达到后的手动触发

**问题描述**：
PRD 5.4.7 说达到上限后"强制停止自动触发"。但 feature_list.md CHAT-07 支持"重新生成"。用户手动点击"重新生成"是否受上限约束？

**备选项**：
- **A. 上限只约束自动触发，不约束手动操作**：用户可以随时手动重新生成或强制触发某 Agent。
- **B. 上限是硬性限制，任何触发都受约束**：包括重新生成。用户必须先发送消息重置计数。
- **C. 重新生成替换原消息，不增加计数**：重新生成是替换已有 Agent 消息，不增加消息计数，因此不受限制。

**推荐：A + C**。重新生成是替换已有消息（不增加计数），自然不受限制。手动强制触发也应有权限绕过上限，否则用户会被系统"锁住"。
回答：到达上限后，用户可通过一个按钮重置上限计数，以当前会话的聊天记录，触发所有agent的一次会话。

### Q13. 编辑 Agent 后历史会话的影响范围

**问题描述**：
feature_list.md AGT-02 备注"编辑后可选是否影响历史会话的 Prompt"。这个"可选"的机制是什么？

**场景**：用户修改了 Alice 的详细人设，已存在的私聊和群聊中，Alice 的 Prompt 是立即生效，还是保持旧人设？

**备选项**：
- **A. 立即全局生效**：编辑 Agent 后，所有现有会话中该 Agent 的 Prompt 立即使用新人设。实现最简单。
- **B. 编辑时让用户选择**：弹出对话框"是否更新现有会话？"，选择"是"则全局更新，"否"则仅影响未来会话。需要为每个会话存储 Agent 人设的快照。
- **C. 仅影响未来会话**：已存在的会话保持创建时的人设。用户可以在会话设置中手动"同步最新人设"。

**推荐：A**。B 和 C 都需要人设版本管理和快照，大幅增加复杂度。角色扮演用户通常期望修改后立即生效。
回答：A立刻生效，在修改后，每次调用的prompt就应该以新的人设进行拼接。

### Q14. 头像存储路径规范

**问题描述**：
schema.md 中 `agents.avatar_path` 和 `group_sessions.avatar_path` 没有定义路径格式。是绝对路径还是相对路径？

**备选项**：
- **A. 绝对路径**：存储完整文件系统路径（如 `C:\Users\...\AgentStage\avatars\alice.png`）。简单，但数据库不可迁移（换电脑后路径失效）。
- **B. 相对路径（推荐）**：相对于应用数据目录的相对路径（如 `avatars/alice.png`）。数据库可迁移，但需要应用启动时解析为绝对路径。
- **C. 内联 Base64**：小头像直接存储在数据库中。适合简单场景，但不适合大量/大图。

**推荐：B**。这是桌面应用的标准做法。应用数据目录下创建 `avatars/` 子目录，数据库只存相对路径。
回答：B，采用标准方案。

### Q15. `trigger_states.last_trigger_time` 的全局性

**问题描述**：
`trigger_states` 是 per-Agent 全局的。Agent 在私聊A被触发后，群聊B中的触发也要等间隔。这是否符合预期？

**场景**：Agent Alice 在私聊中于 t=0 被触发。t=10 时群聊中有新消息，Alice 的间隔未满足，不触发。用户可能期望群聊和私聊是独立的。

**备选项**：
- **A. 保持全局**（当前设计）：Agent 只有一个全局计时器，所有会话共享。实现最简单，与 PRD "全局最小触发间隔"字面一致。
- **B. 按会话独立计时**：每个 Agent 在每个会话中独立维护 `last_trigger_time`。私聊和群聊互不干扰。需要把 `trigger_states` 改为按 `(agent_id, session_id)` 组合键。
- **C. 按类型独立计时**：私聊一个计时器，群聊一个计时器。`trigger_states` 增加 `context_type` 字段。

**推荐：A**。如果改为按会话独立，Agent 可能在多个会话中同时被触发，API 并发压力更大。全局间隔是 PRD 明确设计的"防轰炸"机制。
回答：保持全局，这个设计类似于人类“隔一段时间查看消息，并且会查看所有消息”的场景，这么说应该更好理解，同时能降低开销。

### Q16. 私聊中用户连续发送多条消息的触发策略

**问题描述**：
PRD 5.4.8 说"用户发送消息后，将消息加入该 Agent 的积压队列，按全局最小间隔规则触发"。如果用户连续快速发送 5 条消息，Agent 是只被触发一次（30秒后统一处理），还是可能被触发多次？

**备选项**：
- **A. 只触发一次**：第一条消息触发定时器，后续消息只追加到 pending_queue，30 秒后统一处理。最符合 PRD 设计。
- **B. 每条消息都尝试触发**：每次用户发消息都检查间隔，不满足就加入队列。效果与 A 相同（因为间隔内只会触发一次），但逻辑上有冗余检查。
- **C. 用户消息聚合**：如果用户在 N 秒内连续发送多条，前端聚合成一条消息（类似微信的合并发送）。减少消息数量。

**推荐：A**。与 PRD 4.2 流程图一致。
回答：同上一题，也就是A，这个在你给出的描述场景中，第一条消息应该立刻触发回答，然后后续4条会在30秒后再次触发一次，此时如果agent已经回复了第一条，在聊天记录中也可以看到ai回复的一条和用户的5条。由于ai回复时参考的内容只有一条，此时的顺序应该是 用户输出1 ai回复1 用户输出2 用户输出3 用户输出4 用户输出5 。这个消息顺序也要在前端保持一致

### Q18. 删除 Agent 时的级联行为

**问题描述**：
schema.md 中 `agents` 表被多个外键引用（private_sessions、friendships、group_members、trigger_states），都设置了 `ON DELETE CASCADE`。删除 Agent 会级联删除其所有私聊、好友关系、群成员记录和消息（通过 session → message 的级联）。

**这是否过于激进？**

**备选项**：
- **A. 保持级联删除**：删除 Agent 即彻底清除所有相关数据。简单直接。
- **B. Agent 软删除**：增加 `agents.is_deleted` 字段。删除时标记为已删除，UI 中隐藏，但历史消息保留（消息表中的 `sender_id` 仍指向该 Agent，只是显示为"已删除角色"）。
- **C. 禁止删除有会话的 Agent**：删除前检查，如果该 Agent 有活跃会话，提示"请先删除相关会话"。

**推荐：B**。用户可能误删 Agent 后希望恢复。软删除是更安全的做法，且 reference.md 提到 SillyTavern 的角色卡是重要资产，不应轻易物理删除。
回答：B，历史消息记录和前面某个问题一样，在数据库保留，前端可在一个已删除会话中查看（对于私聊），对于群聊，如果其中有被删除的角色，保留角色的消息，但显示为“已删除角色”。

### Q19. Tauri Command 设计粒度

**问题描述**：
tech-stack.md 没有明确 Tauri Command 的设计规范。是粗粒度（一个 Command 处理完整业务流程）还是细粒度（CRUD 式 Command）？

**备选项**：
- **A. 粗粒度业务 Command**：如 `send_message(session_id, content)` 一个 Command 完成"写消息→触发 Agent→返回流式响应"全部流程。前端调用简单，但 Command 内部逻辑复杂。
- **B. 细粒度 CRUD Command**：`create_message()`、`trigger_agent()`、`get_stream()` 分开。前端编排业务流，灵活但调用次数多。
- **C. 混合模式**：写操作粗粒度（如 `send_message`），读操作细粒度（如 `get_messages`、`get_session_list`）。

**推荐：C**。写操作涉及事务和副作用，适合封装为粗粒度 Command。读操作可以细粒度，方便前端按需获取。
回答：C。

### Q20. 前端路由方案

**问题描述**：
AgentStage 是单窗口桌面应用，内部有多个功能页面（Agent 列表、聊天界面、设置）。是否需要前端路由库？

**备选项**：
- **A. 不需要路由库**：用 Svelte 5 的 `$state` 管理当前页面状态，条件渲染组件。最简单，因为没有浏览器地址栏和前进/后退需求。
- **B. 使用 `svelte-spa-router`**：轻量级 hash 路由，支持浏览器式导航。过度设计。
- **C. 使用 Tauri 多窗口**：每个功能一个独立窗口。不符合 IM 应用的集成体验。

**推荐：A**。桌面应用不需要 URL 路由，状态管理足够。
回答：A
