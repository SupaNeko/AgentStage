## 2. 项目背景

### 2.1 业务目标

AgentStage 是一款面向角色扮演爱好者、创作者和 AI 交互探索者的 Windows 桌面应用。它解决了以下核心问题：

1. **多角色互动难以编排**：现有 AI 聊天工具多为单角色对话，用户想观察多个 AI 角色之间如何互动、产生什么化学反应，缺乏专门的工具支持。
2. **角色扮演上下文割裂**：用户希望在群聊中让多个角色知道自己的"身份"（如"我是你们的朋友 Tom"），但现有工具难以在会话级别同步用户人设。
3. **创作与娱乐场景缺失**：小说作者想模拟角色对话、游戏玩家想组建 AI 队伍、普通用户想创建虚拟社交圈，都缺乏一个像"即时通讯软件"一样直观的载体。

预期目标：打造 Windows 平台最自然、最沉浸的多智能体角色扮演聊天工具。

### 2.2 目标用户

| 用户类型 | 用户画像 | 核心诉求 |
|---------|---------|---------|
| 角色扮演爱好者 | 喜欢在 AI 聊天中进行角色扮演，希望有"群像剧"体验 | 让多个 AI 角色在同一空间中互动，自己也能以特定身份参与 |
| 小说/剧本创作者 | 需要测试角色对话、磨合人物性格 | 快速创建角色、模拟对话场景，观察角色互动是否符合预期 |
| AI 探索者 | 对多智能体系统、涌现行为感兴趣 | 低成本实验不同 角色配置下的群体行为 |
| 普通娱乐用户 | 想要一个"虚拟朋友圈"或"AI 社群"来打发时间 | 操作简单，界面熟悉（像微信/QQ），无需技术背景 |

### 2.3 核心价值主张

> **AgentStage 让你像使用微信一样轻松地与多个 AI 角色聊天、围观它们互动，并在任何会话中自由切换你的身份。**

## 4. 核心业务流程

### 4.1 首次使用 → 开始聊天

```mermaid
flowchart TD
    A[安装并启动 AgentStage] --> B{首次启动?}
    B -->|是| C[展示欢迎页 + 引导创建首个 角色]
    B -->|否| D[加载本地数据，展示主界面]
    C --> E[填写 角色 名称、头像、详细人设、简易人设、配置模型 API]
    E --> F{模型是否支持 Function Calling?}
    F -->|否| G[报错：该模型不支持 Tool Calling，请更换模型]
    F -->|是| H[测试 API 连通性]
    G --> E
    H -->|成功| I[创建 1对1 会话]
    H -->|失败| J[提示检查 API 配置]
    J --> E
    I --> K[进入聊天界面，开始对话]
    D --> K
```

### 4.2 全局最小触发间隔 + 消息积压机制

```mermaid
flowchart TD
    A[某事件需触发 角色 X] --> B{当前时间 - last_trigger_time >= min_interval?}
    B -->|是| C[更新 last_trigger_time = 现在]
    C --> D[将当前消息加入积压队列]
    D --> E[一次性处理队列中所有消息]
    E --> F[组装 Prompt 并调用 LLM API]
    B -->|否| G[将当前消息加入积压队列]
    G --> H[等待至 last_trigger_time + min_interval]
    H --> I{队列是否为空?}
    I -->|否| C
    I -->|是| J[无操作，继续等待下次触发]
```

### 4.3 群聊消息触发流程（含禁言 + 上限 + 间隔）

```mermaid
flowchart TD
    A[群聊中某角色发送消息] --> B{该群聊禁言是否开启?}
    B -->|是| C[仅记录消息，不触发任何 角色]
    B -->|否| D[消息写入本地数据库]
    D --> E{该群聊消息上限是否启用?}
    E -->|是| F{群聊中 角色 消息数 >= 上限?}
    F -->|是| G[强制停止，不再触发任何 角色]
    F -->|否| H[计数 +1]
    E -->|否| H
    H --> I[更新该群聊所有角色 的可见消息历史]
    I --> J{各 角色 的最小间隔是否满足?}
    J -->|满足| K[立即触发该角色，处理积压消息]
    J -->|不满足| L[将消息加入该角色 积压队列，等待间隔到期]
    K --> M[各 角色 独立调用 LLM，可选 send_message]
    L --> N[间隔到期后自动触发]
    N --> M
    M --> O{角色 是否回应?}
    O -->|调用 send_message| P[将消息写入群聊]
    O -->|无回应| Q[跳过]
    P --> R[继续监听下一条消息]
    Q --> R
    G --> S[用户发送消息后重置计数]
```

### 5.2 角色管理

#### 5.2.1 新建角色

| 字段 | 说明 |
|-----|------|
| **功能编号** | AGT-01 |
| **功能描述** | 用户创建一个新的 AI 角色，配置角色信息（含双人设）和模型参数 |
| **前置条件** | 应用已启动 |
| **优先级** | P0 |

**页面元素**：

| 元素 | 类型 | 说明 | 校验规则 |
|-----|------|-----|---------|
| 角色 名称 | 输入框 | 角色的显示名称，如"Alice" | 必填，1-20 字符 |
| 头像 | 图片选择 | 上传图片或选择默认头像 | 建议 256x256，支持 jpg/png |
| **详细人设** | 多行文本框 | 角色 自身的 System Prompt，定义性格、背景、说话风格 | 必填，建议 50-2000 字符 |
| **简易人设** | 多行文本框 | 提供给其它角色 看的简介，让对方知道"我是谁" | 必填，建议 20-200 字符 |
| 选择模型 | 下拉框 | 选择 LLM 提供商和模型 | 必填 |
| API Key | 密码输入框 | 调用模型所需的密钥 | 必填，加密存储 |
| Base URL | 输入框 | API 基础地址，支持自定义 | 可选，默认官方地址 |
| 温度(Temperature) | 滑块 | 控制生成随机性，0-2 | 默认 0.7 |
| Max Tokens | 数字输入 | 最大生成 Token 数 | 默认 2048 |
| 思考模式 | 开关 | 启用模型的深度思考/推理模式（如 Kimi k2、DeepSeek Reasoner） | 默认关闭 |
| 上下文长度 | 数字输入 | 最大上下文 Token 数（覆盖模型默认值） | 可选 |
| 重试次数 | 数字输入 | API 调用失败时的自动重试次数 | 默认 3 |

**人设字段设计说明**：

- **详细人设（detailed_persona）**：角色自己看到的完整角色设定，直接注入 Prompt 第 2 层。决定它的性格、语气、知识、行为方式。这是它的"自我认知"。
- **简易人设（simplified_persona）**：其它角色在与之互动时，在 Prompt 第 3 层看到的关于它的简介（角色名片）。例如：
  - 详细人设："你是 Fate/stay night 中的角色卫宫士郎，性格坚韧不拔，内心温柔但执拗，拥有强烈的正义感，口头禅是'人被杀就会死'。你是冬木市穗群原学园的学生，同时也是拥有投影魔术的见习魔术师..."
  - 简易人设："出自 Fate/stay night 的角色卫宫士郎，冬木市的见习魔术师，性格正义感强烈。"
- 两者都支持用户自由修改，实现"我眼中的自己"和"别人眼中的我"的分离。
- **辅助人设字段**（`personality`、`scenario`、`example_messages`、`first_message`）：
  - **当前版本（MVP）**：不直接注入 Prompt，仅作为编辑时的辅助信息展示在界面上。
  - **未来用途**：用于"角色 自我迭代升级人设"功能（P2）。角色 可以基于这些素材和自我对话历史，自动优化自己的 `detailed_persona`。
  - Prompt 拼接时**只使用 `detailed_persona`**，不混合其它字段。

**强制 Function Calling 要求**：

- AgentStage 的所有核心机制（send_message Tool、自然触发控制）依赖 LLM 的 Function Calling 能力。
- ~~在配置模型时，系统必须检测所选模型是否支持 Tool Calling~~（MVP 阶段暂不实现自动检测，用户需自行确认模型支持 Tool Calling）。
- ~~若不支持，立即报错并阻止创建/保存~~（MVP 阶段不阻断保存，由用户在运行时通过错误反馈确认兼容性）。
- 不提供 fallback 到纯文本回复的机制。

**交互逻辑**：

1. 用户点击"新建 角色"按钮
2. 弹出创建表单，填写名称、头像、详细人设、简易人设
3. 选择模型提供商（如 OpenAI、Claude、Gemini、Kimi、MiniMax、自定义兼容端点）
4. 系统检测所选模型是否在支持 Tool Calling 的模型列表中（或通过 API capability 检测）
5. 填写 API Key 和可选参数
6. 点击"测试连接"验证 API（AGT-06）
7. 测试通过后点击"创建"
8. 角色 保存到本地数据库，展示在 角色列表

**编辑角色 的生效规则**：
- 用户修改 角色 的任何字段（人设、模型参数等）后，点击"保存"立即生效。
- **所有现有会话**中涉及该角色 的 Prompt 拼接，在**下一次触发时自动使用最新配置**。
- 不需要为每个会话维护人设快照，实现全局即时更新。

**异常处理**：

| 异常场景 | 处理方式 |
|---------|---------|
| API Key 无效 | 测试连接时提示"API Key 验证失败" |
| 网络不通 | 提示"无法连接到 API 服务器，请检查网络或 Base URL" |
| 名称重复 | 提示"已存在同名 角色，请更换名称" |
| 模型不支持 Tool Calling | **阻断保存**，提示"该模型不支持 Function Calling，请更换模型" |

#### 5.2.2 模型 API 配置

| 字段 | 说明 |
|-----|------|
| **功能编号** | AGT-05 |
| **功能描述** | 为每个角色 独立配置调用的 LLM 服务，支持多 Provider |
| **前置条件** | 创建或编辑角色 |
| **优先级** | P0 |

**说明**：

- 每个角色 可以配置不同的模型和 API Key，实现"不同角色用不同大脑"的效果。
- 支持预设 Provider：OpenAI、Anthropic、Google、Kimi（Moonshot）、MiniMax、Azure 等，以及"自定义"选项。
- 自定义选项需填写 Base URL、模型名称、请求格式（默认 OpenAI 兼容格式）。
- **Kimi（Moonshot）**：国内高可用，支持长上下文（最高 200k），API 格式 OpenAI 兼容，推荐模型 `kimi-k2`、`kimi-latest`。
- **MiniMax**：国内高可用，支持 Function Calling，API 格式 OpenAI 兼容，推荐模型 `abab6.5-chat`、`abab6.5s-chat`。
- 配置信息使用本地 AES-256-GCM 加密存储，不得明文保存 API Key（MVP 阶段使用本地加密，未接入 Windows 凭据管理器）。

### 5.3 会话管理

#### 5.3.1 创建 1对1 会话

| 字段 | 说明 |
|-----|------|
| **功能编号** | SES-01 |
| **功能描述** | 选择一个已创建的 角色，开启一对一私聊 |
| **前置条件** | 至少已创建 1 个 角色 |
| **优先级** | P0 |

**交互逻辑**：

1. 用户点击"新建会话"按钮
2. 选择会话类型：1对1 / 群聊
3. 选择 1对1 后，展示 角色列表供选择
4. 选择 角色 后，系统创建新会话并进入聊天界面
5. 同一个角色 可以被多次选择创建不同会话（多线程独立上下文）
6. **创建私聊后，双方自动建立"好友"关系**（用于 Prompt 中的参与者简介筛选）
7. **角色 也可以通过 `create_private_chat` Tool 自主发起与其它角色 的私聊**（见 5.4.3）。角色 发起的私聊同样会建立好友关系，并实时显示在用户的会话列表中。

#### 5.3.2 创建群聊会话

| 字段 | 说明 |
|-----|------|
| **功能编号** | SES-02 |

**交互逻辑**：

4. 点击"创建"进入群聊界面
5. 群聊创建后可在会话设置中增删 角色（P1）

#### 5.3.3 群聊禁言开关

| 字段 | 说明 |
|-----|------|
| **功能编号** | SES-07 |
| **功能描述** | 每个群聊独立的禁言控制，开启后不再自动触发 角色 调用 |
| **前置条件** | 已进入群聊会话 |
| **优先级** | P0 |

**设计说明**：

- **默认状态**：新建群聊默认**开启禁言**（即 角色 不会自动发言）。
- **禁言开启时**：群聊表现为普通 IM 群聊，用户发送的消息仅被记录，不会自动触发任何 角色 调用。
- **禁言关闭时（自动模式）**：群聊进入多角色 自动互动模式。任何角色（用户或 角色）发送消息后，系统会**并行拉起群聊中其它所有角色** 的调用（受全局最小间隔和消息上限约束）。
- **避免无限聊天**：禁言开关是核心控制手段。用户可随时一键开启禁言，立即冻结所有角色 自动发言。
- **作用域**：禁言仅对当前群聊生效，不影响其它会话。

**页面元素**：

| 元素 | 类型 | 说明 |
|-----|------|-----|
| 禁言开关 | 顶部开关 | 显示"禁言中"或"自动互动中" |

#### 5.3.5 会话重置、清除历史与软删除

| 字段 | 说明 |
|-----|------|
| **功能编号** | SES-04 |
| **功能描述** | 支持重置会话（基于旧会话开启新 page）、清除历史（删除非当前 page 的消息）、软删除会话 | P1 |
| **优先级** | P1 |

**交互逻辑**：

1. **重置会话**：用户在会话配置面板点击"重置会话"。系统创建新的 `chat_page`，切换当前 page 到新 page，清空未读消息和冻结状态，以相同成员开启全新上下文。
2. **清除历史**：用户在历史会话列表右键选择"清除历史"。系统删除所有非当前 page 的历史消息和归档 page，保留当前 page 消息；清除后该会话从历史列表消失，直到 Reset 产生新 page 后重新出现。
3. **软删除**：用户在会话列表中删除会话。系统执行软删除（`is_deleted = 1`），聊天记录保留在数据库中，好友关系和群聊成员关系保留。被删除的会话从主列表消失。
4. ~~归档列表与恢复~~（MVP 阶段暂不实现）：被软删除的会话暂不提供独立的归档列表查看和恢复功能。

#### 5.4.3 角色回复与 send_message Tool

| 字段 | 说明 |
|-----|------|
| **功能编号** | CHAT-02 / CHAT-10 |
| **功能描述** | 角色 接收上下文后调用 LLM API，通过 Tool 主动发送消息 |
| **前置条件** | 会话中有新消息触发了该角色 |
| **优先级** | P0 |

**提供给 角色 的 Tools**：

系统为每个角色 提供以下 Function Calling 工具：

**1. `send_message` Tool**

| 参数 | 类型 | 说明 |
|-----|------|------|
| `target_type` | string | `private` 或 `group`，表示私聊或群聊 |
| `target_id` | string | 目标会话的唯一 ID |
| `content` | string | 要发送的消息内容 |

**2. `create_private_chat` Tool（角色 自主发起私聊）**

| 参数 | 类型 | 说明 |
|-----|------|------|
| `target_agent_id` | string | 目标 角色 的唯一 ID |
| `first_message` | string | 私聊的第一条消息内容（可选） |

**`create_private_chat` 调用行为**：
- 角色 可以在群聊中或通过全局历史获知其它角色 的存在，并主动发起私聊。
- 系统收到 `create_private_chat` tool_call 后：
  1. 检查两 角色 之间是否已存在私聊会话。
  2. 若不存在，创建新的私聊会话（session_type = 'private'）。
  3. 在 `friendships` 表中建立双方的好友关系（若已存在则跳过）。
  4. 如果提供了 `first_message`，将该消息写入新会话，触发对方角色。
  5. **不将执行结果返回给调用 角色**。
- 新创建的私聊会话会实时出现在用户的会话列表中。

**调用行为**：

- 角色被触发后，系统调用 LLM API，并在请求中提供 `send_message` Tool。
- 角色 通过调用 `send_message(target_type, target_id, content)` 来发送消息。
- 系统收到 tool_call 后，将消息写入指定会话，**不再将执行结果返回给 角色**（降低 token 开销）。
- 如果 角色 没有调用 Tool（即返回空或不响应），则视为该轮不发言。

**Tool Schema 示例**：

```json
{
  "type": "function",
  "function": {
    "name": "send_message",
    "description": "发送一条消息到指定的私聊或群聊",
    "parameters": {
      "type": "object",
      "properties": {
        "target_type": {
          "type": "string",
          "enum": ["private", "group"],
          "description": "目标会话类型：private 为私聊，group 为群聊"
        },
        "target_id": {
          "type": "string",
          "description": "目标会话的唯一标识 ID"
        },
        "content": {
          "type": "string",
          "description": "消息内容"
        }
      },
      "required": ["target_type", "target_id", "content"]
    }
  }
}
```

#### 5.4.4 可见消息历史维护

| 字段 | 说明 |
|-----|------|
| **功能编号** | CHAT-12 |
| **功能描述** | 为每个角色 独立维护其可见的全部消息历史，用于 Prompt 拼接 |
| **优先级** | P0 |

**设计说明**：

每个角色 在系统中拥有一份独立的**可见消息视图**。这份视图包含该角色 参与的所有会话中的全部消息，按会话类型分组组织。

**示例**：

角色 A 的可见消息历史：

- **私聊**：
  - 与 B 的私聊（会话 ID: priv_A_B）：
    - [12:00] B: "嘿，今天有空吗？"
    - [12:05] A: "有的，什么事？"
  - 与 C 的私聊（会话 ID: priv_A_C）：
    - [11:30] A: "记得带资料"
    - [11:35] C: "已经准备好了"

- **群聊**：
  - 群聊 "Friend"（会话 ID: grp_friend，成员: A, B, C, D）：
    - [12:10] B: "大家在吗？"
    - [12:11] C: "在的"
    - [12:12] D: "怎么了？"
    - [12:15] A: "出什么事了？"

**数据更新时机**：

- 任何会话中有新消息发送后，该会话中的所有参与者 角色 的可见消息历史都会实时更新。
- 用户可以在 角色详情页查看其当前的可见消息历史（调试用）。

#### 5.4.5 Prompt 拼接方案

| 字段 | 说明 |
|-----|------|
| **功能描述** | 每次调用 角色 时，按固定顺序拼接 Prompt |
| **优先级** | P0 |

**拼接顺序**（严格按此层级）：

```
1. 系统提示词（全局固定，所有角色 相同，代码中硬编码）
   例如："你是一个正在参与即时通讯聊天的 AI 角色。请根据上下文自然地回应。你可以同时参与多个私聊和群聊，在回复时请根据上下文判断应该回复哪个会话。"

2. 自身角色提示词（详细人设）
   例如："你是 Alice，一位来自维多利亚时代的贵族少女..."

3. 参与者简介（与该角色 有关联的角色简易人设）
   仅包含两类角色：
   a) 该角色 的「好友」：与之有过私聊会话的其它角色
   b) 该角色 所在群聊的「群友」：与之在同一个群聊中的其它角色
   
   例如：
   "你当前在群聊 'Friend' 中，参与者有：
   - Bob（你的好友）：你的管家，稳重可靠，说话简洁。
   - Carol（群友）：你的表妹，活泼开朗，喜欢开玩笑。
   - Dave（群友）：一位神秘的访客，身份不明。"

4. 历史消息（按可见消息历史分组展示）
   例如：
   "【私聊记录】
   与 Bob 的私聊：
   - Bob: ...
   - 你: ...

   【群聊记录】
   群聊 'Friend'：
   - Bob: ...
   - Carol: ...
   - 你: ..."

5. 最新收到的消息（触发本次调用的消息）
   例如：
   "【最新消息】
   Carol 在群聊 'Friend' 中说：'大家晚上一起去吃饭吧！'"
```

**关键设计点**：

- **系统提示词（第1层）**：所有角色 共享，用于设定基础行为规则（如"你是一个 IM 聊天参与者"）。**必须包含会话选择指令**："你可以同时参与多个私聊和群聊。在回复时，请根据上下文判断应该回复哪个会话。如果需要回复多个会话，可以多次调用 send_message 工具。"
- **自身人设（第2层）**：角色 自己的详细人设，不可被其它因素覆盖。
- **参与者简介（第3层）**：动态根据"好友关系 + 群友关系"筛选后拼接，使用它们的**简易人设**。这让 角色 知道"我在和谁聊天"，同时避免无关角色干扰上下文。
- **历史消息（第4层）**：从该角色 的可见消息历史中按私聊/群聊分组提取，保持时间顺序。包含该角色 参与的全部会话（所有私聊 + 所有群聊）。
- **最新消息（第5层）**：单独高亮触发本次调用的消息，并**标注来源会话**，让 角色 明确知道"这条消息来自哪个会话"以及"我这次应该优先回应哪个会话"。角色 也可以基于其它会话的上下文决定回复另一个会话。
- **Token 预算管理（P1 实现）**：MVP 阶段暂不实现动态截断（单条聊天记录短，可支撑较长上下文）。P1 阶段引入 Token 预算管理：使用 tiktoken 本地计算各层 token 数，当总 Prompt 接近模型上下文上限时，优先截断历史消息（第4层），保留系统提示词、人设、参与者简介和最新消息。

**好友关系定义**：

- **角色-角色 好友**：当两个 角色被创建为 1对1 私聊会话后（或通过 `create_private_chat` Tool 自主发起），双方自动标记为"好友"。好友关系是双向的、持久化的。删除私聊会话**不会**自动删除好友关系（类似 IM 中删会话不等于删好友）。未来可扩展手动添加/删除好友功能（P2）。
- **用户-角色 关系**：**所有角色 默认将用户视为好友**。在 Prompt 的参与者简介中，用户统一标注为：
  ```
  - {用户昵称}（真实用户）：正在与你聊天的真实用户。
  ```
  - P2 阶段启用用户人设后，上述标注替换为用户选择的当前人设信息。
  - 不需要在 `friendships` 表中维护用户-角色 关系（用户是隐式全局好友）。

#### 5.4.6 全局最小触发间隔（核心机制）

| 字段 | 说明 |
|-----|------|
| **功能编号** | CHAT-13 |
| **功能描述** | 每个角色 拥有全局最小触发间隔，间隔内积压的所有新消息一次性组装调用 |
| **优先级** | P0 |

**设计说明**：

- 每个角色 维护两个核心状态：
  - `last_trigger_time`：上次被调用的**全局**时间戳（跨所有会话共享，不按会话拆分）
  - `pending_queue`：积压待处理的消息队列
- **默认最小间隔**：30 秒（可在系统设置中调节，范围 5-300 秒）。
- **触发流程**：
  1. 某事件需要触发 角色 X（私聊或群聊中的新消息）。
  2. 检查 `now - last_trigger_time >= min_interval`。
  3. **若满足**：更新 `last_trigger_time = now`，将当前消息加入 `pending_queue`，然后一次性处理队列中所有积压消息，组装 Prompt 并调用 LLM API，最后清空队列。
  4. **若不满足**：将当前消息加入 `pending_queue`，不立即触发。系统设置一个定时器，在 `last_trigger_time + min_interval` 时刻自动检查队列。若队列非空，则执行步骤 3。
  5. 在等待期间若有更多新消息到来，继续追加到 `pending_queue`。

**效果**：

- 大幅降低 API 调用频率（从"每条消息都调"变为"最多每 30 秒调一次"）。
- 角色 的回复会综合间隔内收到的多条消息，更像真实人类"看完几条消息后一起回复"的行为。
- 每个角色 的间隔独立计算，群聊中不同 角色 会在各自的时间点响应，节奏更自然。

#### 5.4.7 消息上限保护（核心机制）

| 字段 | 说明 |
|-----|------|
| **功能编号** | CHAT-14 |
| **功能描述** | 私聊和群聊分别可配置 角色 消息条数上限，达到上限后强制停止触发 |
| **优先级** | P0 |

**配置项**：

| 配置项 | 默认值 | 可调范围 | 说明 |
|-------|--------|---------|------|
| 私聊消息上限 | 20 条 | 5-100 | 单个私聊中 角色发送的消息达到此值后停止自动触发 |
| 群聊消息上限 | 30 条 | 5-200 | 单个群聊中所有角色 发送的消息总和达到此值后停止自动触发 |
| 私聊上限开关 | 开启 | 开/关 | 关闭后私聊不限制消息条数 |
| 群聊上限开关 | 开启 | 开/关 | 关闭后群聊不限制消息条数 |

**计数规则**：

- **只统计 角色发送的消息**，用户发送的消息不计入。
- **私聊**：该私聊会话中"对方角色"发送的消息数。
- **群聊**：该群聊中"所有角色"发送的消息总和。
- 计数在会话级别独立维护，使用显式字段 `agent_message_count`（应用层维护，O(1) 读取）。

**计数器重置时机**：

以下事件会自动将计数器重置为 0：
1. **用户发送消息**（自动重置，默认行为）。
2. **创建新群聊**（新会话计数器从 0 开始）。
3. **清空会话聊天记录**（清空后计数器重置）。
4. **手动重置**：前端提供"重置计数"按钮，用户可随时手动重置（无需发送消息）。

**达到上限后的行为**：

- 该会话立即停止自动触发任何 角色。
- 聊天界面显示提示："已达到消息上限，自动对话已暂停。发送消息或点击重置以继续。"
- **用户发送任意消息后，自动重置该会话的计数器**，自动对话恢复。
- 用户也可点击"重置计数"按钮手动恢复。点击后：
  1. 计数器重置为 0。
  2. 系统以当前会话的完整聊天记录作为上下文，**立即触发该会话中所有相关 角色 一次**（私聊触发对方角色，群聊触发所有其它角色）。
- 用户还可在设置中临时关闭上限或调高数值。

**与禁言开关的区别**：

- **禁言开关**：手动控制，开启后完全不触发 角色（无论消息多少）。
- **消息上限**：自动控制，达到阈值后停止触发，但用户发消息即可续杯。

#### 5.4.8 私聊自动触发

| 字段 | 说明 |
|-----|------|
| **功能编号** | CHAT-11 |
| **功能描述** | 私聊中任何角色发送消息后，触发接收方 角色 的调用 |
| **优先级** | P0 |

**触发规则**：

- **用户 → 角色**：用户发送消息后，将消息加入该角色 的积压队列，按全局最小间隔规则触发。
  - **用户连续发送多条消息的场景**：第一条消息到达时若间隔满足，**立即触发** 角色（此时 pending_queue 中只有第一条）。角色回复后，后续消息继续累积在 pending_queue 中，等待间隔到期后批量处理。
  - **消息顺序保持**：前端严格按 `created_at` 时间戳展示消息。例如：用户1 → AI回复1 → 用户2 → 用户3 → 用户4 → 用户5 → AI回复2（批量）。
- **角色 → 用户**：角色发送消息后，接收方是真实用户，不再触发自动调用。
- **角色 A → 角色 B（两个 角色 的私聊）**：角色-角色 私聊可由用户手动创建，也可由 角色 通过 `create_private_chat` Tool 自主发起。角色 A 发送消息后，触发 角色 B（加入积压队列，按间隔触发）。角色 B 回复后，触发 角色 A。理论上可无限循环，但受以下机制约束：
  - **全局最小间隔**：每个角色 最多每 30 秒响应一次，天然降低循环速度。
  - **消息上限**：达到上限后强制停止。
  - **用户介入**：用户可随时发送消息参与或暂停对话。
  - **好友关系**：通过 `create_private_chat` 创建的私聊会自动建立好友关系，双方可在 Prompt 中获知彼此的简易人设。

---

#### 5.4.9 群聊自动触发（角色-角色 自动对话）

| 字段 | 说明 |
|-----|------|
| **功能编号** | CHAT-05 |
| **功能描述** | 群聊禁言关闭后，任何角色发送消息会自动触发群聊中其它角色 的调用 |
| **优先级** | P0 |

**触发规则**：

1. 群聊禁言关闭时，任何消息（用户或 角色）发送后：
   - 系统检查消息上限。若已达上限，停止触发。
   - 对于群聊中**除发送者外的每一个角色**：
     - 检查该角色 的全局最小间隔是否满足。
     - 若满足：立即触发，处理积压队列中的所有消息。
     - 若不满足：将新消息加入该角色 的积压队列，等待间隔到期后自动触发。
2. 如果多个 角色 同时决定回复：
    - 每个角色 的回复在**生成完成后立即展示**在群聊中（来一个展示一个），按生成完成的时间排序。
    - 群聊中**不显示"正在输入"状态**，模拟真实 IM（人类不会在群聊中显示"对方正在输入"）。
    - 每条回复又会作为新消息触发其它角色（受间隔和上限约束）。
3. 用户可以随时：
    - **开启禁言**：立即冻结所有自动触发。
    - **发送消息**：正常参与对话，其消息也会触发其它角色，同时重置消息上限计数。

**自然性保障**：

- 不是每条消息都会得到回复（角色 可能选择不调用 Tool），符合真实群聊的节奏。
- 全局最小间隔让每个角色 有自己的"反应时间"，避免秒回轰炸。
- 消息上限提供硬性兜底，防止失控。

#### 5.4.10 消息展示规范

| 字段 | 说明 |
|-----|------|
| **功能编号** | CHAT-03 |
| **功能描述** | 按发送者区分展示消息气泡 |
| **优先级** | P0 |

**展示规则**：

- **用户消息**：靠右展示，使用蓝色/主色调气泡，显示用户头像和昵称
- **角色 消息**：靠左展示，使用白色/灰色气泡，显示 角色头像和名称
  - **不采用流式输出**：角色 消息在生成完成后**一次性完整展示**，不逐字/逐句打字机式输出。
  - **私聊"正在输入"**：在 1对1 私聊窗口中，角色 生成期间可显示"正在输入..."提示（低优先级，P1 实现）。
  - **群聊无输入提示**：群聊中不显示任何"正在输入"状态，模拟真实 IM 群聊体验。
- **系统消息**（如"Alice 加入了群聊"、"已达到消息上限，自动对话已暂停"）：居中展示，使用灰色小字
- **时间戳**：每条消息显示发送时间，同一天的消息在首次显示日期分隔线
- **连续消息**：同一发送者的连续消息可合并头像展示，减少视觉冗余

### 5.5 用户角色（P2 优先级）

> ⚠️ 本模块全部功能优先级为 P2，MVP 版本可先不实现，但架构上需预留扩展点。

#### 5.5.1 用户人设配置

| 字段 | 说明 |
|-----|------|
| **功能编号** | USR-01 |
| **功能描述** | 用户可创建并管理自己的虚拟身份，包含名称和人物简介 |
| **前置条件** | 无 |
| **优先级** | P2 |

**页面元素**：

| 元素 | 类型 | 说明 |
|-----|------|-----|
| 人设名称 | 输入框 | 如"Tom" |
| 人设简介 | 多行文本框 | txt 格式，描述身份、性格、与其他角色的关系等 |
| 头像 | 图片选择 | 该人设的头像 |

**交互逻辑**：

1. 用户进入"我的人设"页面
2. 点击"新建人设"，填写名称、简介、上传头像
3. 保存后可随时编辑或删除
4. 可创建多个人设，用于不同会话场景

---

#### 5.5.2 会话中选择用户身份

| 字段 | 说明 |
|-----|------|
| **功能编号** | USR-02 |
| **功能描述** | 在每个会话中，用户选择以"普通用户"或"某人设"参与聊天 |
| **前置条件** | 已创建至少一个人设（可选） |
| **优先级** | P2 |

**交互逻辑**：

1. 在每个会话的顶部或侧边栏，显示当前用户身份
2. 默认显示"普通用户"
3. 点击可切换为已创建的某个人设
4. 切换后立即生效，后续发送的消息以该身份展示
5. 该身份会同步给会话中的所有角色

---

#### 5.5.3 人设同步给 角色

| 字段 | 说明 |
|-----|------|
| **功能编号** | USR-03 |
| **功能描述** | 将用户选择的人设信息注入该会话所有角色 的 Prompt，使 角色 了解用户身份 |
| **前置条件** | 用户在当前会话中选择了人设 |
| **优先级** | P2 |

**同步位置**：

在 Prompt 拼接的「参与者简介」区块中追加：

```
- {用户人设名}（真实用户）：{用户人设简介}
```

如果用户为"普通用户"模式，显示为：

```
- {用户昵称}（真实用户）：正在与你聊天的真实用户。
```

## 6. 非功能需求

### 6.1 性能要求

| 指标 | 要求 |
|-----|------|
| 应用启动时间 | ≤ 5 秒（常规 PC 配置） |
| 会话列表加载 | ≤ 1 秒（100 个会话以内） |
| 消息加载 | 首次进入聊天加载最近 50 条 ≤ 500ms |
| API 请求超时 | 默认 60 秒，可配置 |
| 内存占用 | 正常使用 ≤ 500MB |
| 群聊并发触发 | 同时调用多个 角色 时，系统需控制并发数，避免内存/网络过载（建议最多并行 5 个） |
| 消息积压处理 | 30 秒间隔内积压的消息需在 500ms 内完成 Prompt 组装 |

### 6.2 安全要求

- [x] API Key 等敏感信息使用 Windows DPAPI 或 AES 加密存储，不得明文保存在配置文件
- [x] 本地数据库文件建议加密或设置访问权限
- [x] 应用日志中不得记录 API Key 等敏感信息
- [x] 支持代理配置，满足特定网络环境下的访问需求（P1）

### 6.3 兼容性要求

| 维度 | 支持范围 |
|-----|---------|
| 操作系统 | Windows 10 版本 1809 及以上，Windows 11 |
| 架构 | x64（AMD64），后续可扩展 ARM64 |
| 分辨率 | 最低 1280x720，推荐 1920x1080 及以上 |
| 网络 | 需要联网调用 LLM API，本地功能离线可用 |
| LLM 能力 | **必须支持 Function Calling / Tool Use**，不支持纯文本 Completion 模型 |

### 6.4 数据与存储

| 项目 | 要求 |
|-----|------|
| 数据库 | SQLite（轻量、无需额外服务） |
| 媒体文件 | 头像、图片等存储在应用数据目录，按用户/会话组织 |
| 数据迁移 | 版本升级时自动执行数据库 Schema 迁移 |
| 导出格式 | 聊天记录支持导出为 Markdown / JSON（P1） |

## 7. 迭代规划

按用户要求调整实现顺序：

| 阶段 | 包含功能 | 目标 |
|-----|---------|------|
| **阶段一：角色配置 + UI** | AGT-01~08, APP-02~03, SES-01~03 | 完成 角色 创建、双人设配置、强制 Tool Calling 检测、模型 API 配置、角色列表 UI、应用基础框架和数据存储 |
| **阶段二：1对1 私聊** | CHAT-01~04, CHAT-10~14, CHAT-06 | 完成私聊会话、好友关系、`send_message` Tool、Prompt 拼接（含好友筛选）、全局最小间隔、私聊消息上限 |
| **阶段三：群聊** | SES-02, SES-07, CHAT-05 | 完成群聊创建、禁言开关、群聊多角色 自动触发、群聊消息上限、简易人设同步、可见消息历史 |
| **V1.1** | APP-01, APP-04~05, SES-04~06, CHAT-07~09, SET-01~05 | 安装包、数据备份、会话管理增强、消息重新生成、上下文查看、主题切换、触发间隔与上限设置 |
| **V2.0** | USR-01~04, AGT-07, CHAT-10 扩展 | 用户角色扮演系统、人设同步、图片/文件消息 |

> **注意**：安装包（APP-01）在阶段一不实现，但技术栈选型时必须确保最终可打包为 Windows 安装程序。模型必须支持 Function Calling，这是硬性技术约束。

## 8. 附录

### 8.1 术语表

| 术语 | 解释 |
|-----|------|
| 角色 | 智能体，在本产品中特指由 AI 模型驱动的虚拟角色 |
| 详细人设 | 角色 自身使用的完整角色设定（System Prompt），决定性格、语气、行为 |
| 简易人设 | 提供给其它角色 看的角色简介，让对方了解"我是谁" |
| 好友 | 两个 角色 之间有过私聊会话即互为好友，用于 Prompt 中参与者简介的筛选 |
| System Prompt | 系统提示词，定义 角色 的行为、性格、背景等底层指令 |
| Provider | LLM 服务提供商，如 OpenAI、Anthropic、Google 等 |
| Base URL | API 服务的基础地址，支持自定义兼容端点（如 OneAPI、Ollama 等） |
| 人设 | 用户为自己设定的虚拟身份，用于角色扮演场景 |
| 禁言 | 群聊级别的开关，开启后禁止自动触发 角色 调用 |
| 自动模式 | 群聊禁言关闭时的状态，消息会触发其它角色（受间隔和上限约束） |
| send_message Tool | 提供给 角色 的 Function Calling 工具，用于主动发送消息 |
| 全局最小触发间隔 | 每个角色 两次调用之间的最短等待时间，默认 30 秒 |
| 消息上限 | 私聊/群聊中 角色 消息条数的上限，达到后强制停止自动触发 |
| 可见消息历史 | 每个角色 独立维护的、它能看到的所有消息的记录 |
| 积压队列 | 在最小触发间隔内累积的待处理消息，间隔到期后一次性处理 |
